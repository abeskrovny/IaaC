# Подготовительные действия
Мой выбор пал на реализацию в Docker-окружении и обусловлен необходимостью обеспечить быстрое развертывание, полную воспроизводимость стенда и строгую изоляцию сервисов на одном хосте. Использование декларативной конфигурации (`docker-compose.yml`) позволяет зафиксировать точные версии компонентов и исключить конфликты зависимостей с основной операционной системой, минимизируя влияние различий в настройках серверов.

Кроме того, контейнеризация упрощает сопровождение и масштабирование инфраструктуры: сетевые взаимодействия между сервисами инкапсулированы во внутренней сети Docker, а привязка к выделенным IP-адресам хоста позволяет избежать пересечения стандартных портов. Такой подход ускоряет восстановление сервисов при сбоях, упрощает обновление версий и делает архитектуру решения прозрачной для всех участников команды.

Первоначально, необходимо установить сам пакет Docker'а:
```bash
sudo apt install -y docker.io docker-compose-v2
```

Проверить наличие установленного пакета можно через запрос его версии:
```bash
admin@srvOoBService01:/opt/netbox-docker$ docker -v
Docker version 29.1.3, build 29.1.3-0ubuntu4.1
```




---

Однако, функционал пайплайна можно запустить в рамках одного хоста. Для этого надо навесить дополнительные IP-адреса на сетевой интерфейс хоста, привязать каждый контейнер к собственному IP при публикации портов и при этом объединить все контейнеры в общую пользовательскую сеть bridge-драйвера.

#### Шаг 1. Настройка дополнительных IP-адресов на хосте
Сначала выполним действия на стороне хоста: работать будет в адресном пространстве IPv4:
```bash
admin@srvOoBService01:~$ ip -4 addr show ens3
2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc pfifo_fast state UP group default qlen 1000
    altname enp0s3
    altname enx005000000500
    inet 10.1.111.11/24 brd 10.1.111.255 scope global ens3
       valid_lft forever preferred_lft forever
```

В моем случае видно, что адрес указан статически. Поэтому привязка дополнительных IP-адресов значительно упрощается:
```bash
ip addr add 10.1.111.12/24 dev ens3
ip addr add 10.1.111.13/24 dev ens3
ip addr add 10.1.111.14/24 dev ens3
```

Указанные выше настройки будут работать до перезагрузки, поэтому желательно данные настройки произвести перманентно.

Если это Ubuntu (как в моем случае), то в современных версиях (начиная с 17.10) сетевые настройки хранятся в YAML-файлах в директории `/etc/netplan/`. Система `Netplan` читает эти файлы и сама передает конфигурацию в сетевой демон (`systemd-networkd` на серверах или `NetworkManager` на десктопах).

Узнать, какие файлы и настройки реально применил Netplan, можно с помощью команды `sudo netplan status`:
```bash
admin@srvOoBService01:~$ sudo netplan status --all
     Online state: online
    DNS Addresses: 127.0.0.53 (stub)
       DNS Search: oob.local

●  1: lo ethernet UNKNOWN/UP (unmanaged)
      MAC Address: 00:00:00:00:00:00
        Addresses: 127.0.0.1/8
                   ::1/128

●  2: ens3 ethernet UP (networkd: ens3)
      MAC Address: 00:50:00:00:05:00 (Red Hat, Inc.)
        Addresses: 10.1.111.11/24
                   10.1.111.12/24
                   10.1.111.13/24
                   10.1.111.14/24
                   fe80::250:ff:fe00:500/64 (link)
    DNS Addresses: 10.1.111.254
                   8.8.8.8
       DNS Search: oob.local
           Routes: default via 10.1.111.254 (static)
                   10.1.111.0/24 from 10.1.111.11 (link)
                   fe80::/64 metric 256
...
```

или проверив сгенерированные конфиги в /run/systemd/network/ (для сервера) и /run/NetworkManager/system-connections/ (для десктопа).

Так как разные типы установок по-умолчанию задействуют разные инструменты: `systemd-networkd` создан для статичных, предсказуемых серверных сетей с минимальной нагрузкой, а `NetworkManager` — для динамических пользовательских устройств ( ноутбуков, рабочих станций), где сеть постоянно меняется, необходимо определить, с каким именно мы сейчас имеем дело (сами системы в остальном мало чем отличаются).

Определить инструмент проще всего через получение положительного ответа (`active`) на одну из следующих команд:
```bash
systemctl is-active systemd-networkd
systemctl is-active NetworkManager
```

Так как я использую Ubuntu-сервер, то мой результат вполне предсказуем:
```bash
admin@srvOoBService01:~$ systemctl is-active systemd-networkd
active
admin@srvOoBService01:~$ systemctl is-active NetworkManager
inactive
```

Соответственно, сами скомпилированные `netplan` файлы будут находиться в директории `/run/systemd/network/`:
```bash
admin@srvOoBService01:~$ sudo ls -la /run/systemd/network/
total 12
drwxr-xr-x  2 root root            100 Nov 20 07:25 .
drwxr-xr-x 23 root root            720 Nov 20 11:31 ..
-rw-r-----  1 root root             78 Nov 20 07:25 10-netplan-ens3.link
-rw-r-----  1 root systemd-network 214 Nov 20 07:25 10-netplan-ens3.network
-rw-r--r--  1 root root            131 Sep  9 13:09 zzzz-dracut-default.network
```

где:
- `10-netplan-ens3.link` — параметры низкоуровневой привязки интерфейса (обычно MAC-адрес или имя устройства);
- `10-netplan-ens3.network` — главный рабочий файл, в который Netplan перевел YAML-конфиг при загрузке системы. Именно по нему `systemd-networkd` сейчас держит IP-адреса на интерфейсе `ens3`.
- `zzzz-dracut-default.network` — резервный конфиг ранней загрузки (`initramfs/dracut`), который срабатывает только если более приоритетные файлы (`10-...`) отсутствуют.

Чтобы безопасно добавить несколько IP-адресов на интерфейс `ens3` в Ubuntu Server, необходимо отредактировать YAML-файл в директории `/etc/netplan/`. Их там может быть несколько, при этом если в `/etc/netplan/` лежит несколько YAML-файлов, Netplan читает их все по очереди в алфавитном (лексикографическом) порядке и склеивает в одну общую конфигурацию.
```bash
admin@srvOoBService01:~$ ls -la /etc/netplan/
total 12
drwxr-xr-x   2 root root 4096 Nov 13 15:02 .
drwxr-xr-x 117 root root 4096 Nov 19 06:22 ..
-rw-------   1 root root  384 Nov 13 15:02 00-installer-config.yaml
```

Можно поступить гибче: не трогать базовый файл установщика (`00-installer-config.yaml`), а создать отдельный файл специально под IP-адреса для Docker-контейнеров — например, `/etc/netplan/60-docker-config.yaml` со следующим содержимым:
```yaml
network:
  version: 2
  ethernets:
    ens3:
      addresses:
        - 10.1.111.12/24  # NetBox
        - 10.1.111.13/24  # OpenBao
        - 10.1.111.14/24  # GitLab
```

Netplan сам объединит их с основным IP из первого файла, но желательно поправить его права следующим образом, чтобы не получить предупреждений:
```bash
sudo chmod 600 /etc/netplan/60-docker-config.yaml
```

Чтобы увидеть итоговый «склеенный» конфиг из всех файлов, используем команду `netplan get`:
```bash
admin@srvOoBService01:~$ sudo netplan get
network:
  version: 2
  ethernets:
    ens3:
      match:
        macaddress: "00:50:00:00:05:00"
      addresses:
      - "10.1.111.11/24"
      - "10.1.111.12/24"
      - "10.1.111.13/24"
      - "10.1.111.14/24"
      nameservers:
        addresses:
        - 10.1.111.254
        - 8.8.8.8
        search:
        - oob.local
      set-name: "ens3"
      routes:
      - to: "default"
        via: "10.1.111.254"
```

Применить изменения Netplan без перезагрузки сервера можно командой `sudo netplan apply` или (в моем случае) безопасным вариантом `sudo netplan try`:
```bash
admin@srvOoBService01:~$ sudo netplan try
Do you want to keep these settings?

Press ENTER before the timeout to accept the new configuration

Changes will revert in 114 seconds
```

Утилита проверяит синтаксис, временно применяет новые настройки и запусктит обратный отсчет на 120 секунд. 

Если конфигурация была ошибочной и был потерян доступ к серверу по SSH, через 2 минуты Netplan автоматически вернет предыдущую рабочую конфигурацию. Если же соединение не разорвалось, то надо нажать Enter, чтобы сохранить изменения, о чем, в случае успеха, будет выведено диагностическое сообщение `Configuration accepted.`.

Чтобы в дальнейшем не пересекаться в портах, необходими перенастроить слушатель самого хоста только на основной адрес. В современных версиях Ubuntu (22.10 / 24.04+) порт `22/TCP` по умолчанию слушает не сам сервис `ssh.service`, а сокет-активатор `ssh.socket` (`systemd socket activation`), который игнорирует `ListenAddress` из `sshd_config`.
Из-за этого `systemd` продолжает держать порт `22/TCP` на всех адресах `0.0.0.0:22` и `[::]:22`.

При использовании `ssh.socket` требуется переопределить адрес прослушивания в `systemd`. Сделать это удобнее всего через `sudo systemctl edit ssh.socket`, произведя в открывшемся редакторе следующую коррекцию:
```ini
[Socket]
ListenStream=
ListenStream=10.1.111.11:22
```

> В открывшемся редакторе необъходит обязательно добавить пустую строку `ListenStream=`, чтобы сбросить стандартный биндинг `0.0.0.0:22`.

Если ближе управление через `ssh.service`, то необходимо в файле `/etc/ssh/sshd_config` включить прослушивание директовой `ListenAddress 10.1.111.11` и переключить SSH:
```bash
sudo systemctl disable --now ssh.socket
sudo systemctl enable --now ssh.service
sudo systemctl start --now ssh.service
```

#### Шаг 2. Настройка общей сети Docker
Создадим Docker-сеть с драйвером `bridge` (тип по-умолчанию):
```bash
admin@srvOoBService01:~$ sudo docker network create gitopsnet -d bridge
cde63f699fee423a46c6fd42e65be69e1c81a652b9831c1e63505c66f7ae022c
```

Cозданная через `docker network create` сеть сохраняется после перезагрузки сервера, так как Docker записывает конфигурацию всех пользовательских сетей в свою внутреннюю базу данных (обычно в `/var/lib/docker/network/files/`), а после перезагрузки хоста демон `dockerd` автоматически считывает эту базу и заново поднимает виртуальный мост (`br-...`) с теми же параметрами и именем.

Удалить сеть можно вручную выполнив команду `docker network rm <ИДЕНТИФИКАТОР/ИМЯ>`. Удалиться сеть может и в случае запуска команды очистки неиспользуемых ресурсов `docker network prune` или `docker system prune` в тот момент, когда ни один контейнер не подключен к сети (если к сети подключен хотя бы один запущенный или остановленный контейнер, команда её не тронет).

Чтобы внутренние IP-адреса контейнеров и шлюз сети `gitopsnet` были предсказуемыми и не пересекались с IP-адресацией локальной сети 192.168.1.0/24, можно создавать сеть с явным указанием:
```bash
sudo docker network create --subnet=172.12.11.0/24 -d bridge gitopsnet
```

в резульате чего, получим на хосте следующий интерфейс:
```bash
15: br-4799fda592b6: <NO-CARRIER,BROADCAST,MULTICAST,UP> mtu 1500 qdisc noqueue state DOWN group default 
    link/ether b6:a4:d6:53:7f:4a brd ff:ff:ff:ff:ff:ff
    inet 172.12.11.1/24 brd 172.12.11.255 scope global br-4799fda592b6
       valid_lft forever preferred_lft forever
```

> Статус state `DOWN` и флаг `NO-CARRIER` у виртуального моста (`bridge`) означают лишь то, что к нему прямо сейчас не подключен ни один запущенный контейнер.

#### Шаг 3. Настройки на стороне контейнеров
При поднятии контейнеров, я буду использовать инструмент `Docker Compose`, поэтому сразу опишу свои действия в отношении именно к этому инструменту.

В Docker Compose необходимо настроить привязку портов к конкретным IP хоста и общую пользовательскую сеть `bridge`. Так используемые сервисы смогут слушать стандартные порты (например, 80/443 или 8200) на своем выделенном IP-адресе, а между собой они будут общаться напрямую по именам сервисов.

Здесь проще использовать файлы `docker-compose.override.yml` для каждого развертываемого контейнера — это штатный способ не трогать оригинальные файлы при обновлениях. Docker Compose автоматически подхватывает `docker-compose.override.yml` в той же папке.

Перед запуском `docker compose up -d` необходимо создать файл, аналогичный нижеприведенному (в примере - файл для контейнера Netbox):
```yaml
services:
  netbox:
    ports:
      - "10.1.111.12:80:8080"
    networks:
      - default
      - gitopsnet

networks:
  gitopsnet:
    external: true
```

В Docker Compose действует правило: если у сервиса явно переопределяется блок `networks:`, он автоматически отключается от стандартной сети `default`, если не вписать её в список вручную. Поэтому здесь критически важны обе строки:
- `default` — внутренняя изолированная сеть, которую Docker Compose автоматически создает для текущего проекта (`netbox-docker_default`). В ней работают `postgres`, `redis` и `redis-cache`. Без этой строчки контейнер `netbox` потерял бы связь со своей базой данных и кэшем.
- `gitopsnet` — общая пользовательская сеть типа `bridge`, в которую также включены `GitLab` и `OpenBao`. Благодаря ей контейнеры могут обращаться друг к другу напрямую по именам сервисов (например, http://netbox:8080, http://openbao:8200), минуя внешние IP-адреса хоста и NAT.

Если в инстралляции по тем или иным причинам не используется Docker Compose, то обеспечить описываемую выше связанность можно при запуске контейнеров следующим образом (в примере конфигурация для контейнера OpenBao):
```bash
docker run -d \
  --name openbao \
  --restart unless-stopped \
  --network gitopsnet \
  --cap-add IPC_LOCK \
  -p 10.1.111.13:80:8200 \
  -v /opt/openbao/config:/openbao/config:ro \
  -v /opt/openbao/data:/openbao/data \
  openbao/openbao:latest \
  server -config=/openbao/config/config.hcl
```

Важные нюансы:
- **Исходящий трафик из контейнера**: по умолчанию при обращении контейнера во внешний интернет NAT может использовать основной IP хоста, а не тот, на который повешен порт. Если нужно, чтобы контейнер ходил наружу со «своего» IP, необходимо проверить правила SNAT/MASQUERADE или используйте драйвер `macvlan / ipvlan`, но с ними связь "хост ↔ контейнер" требует отдельной настройки.
- **Файрвол (UFW / iptables)**: Docker сам управляет цепочками `iptables` для проброшенных портов, поэтому требуется убедиться, что правила файрвола не блокируют трафик на нужные IP и порты.
